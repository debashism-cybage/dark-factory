AI-Native Feature Delivery

A context-first model where AI acts as a co-engineer across the full feature lifecycle — not a typing accelerant. AI output quality is bounded by context quality. Your investment is in assembling context, not writing code faster.

📋

Context First

Every feature begins with a Feature Context Document — three layers of structured input before any AI generation starts.

🤝

AI Generates, Humans Decide

Every gate has a human accountable for the output. AI produces artefacts; engineers approve them.

🔒

Gate Before Generate

No phase begins without the prior gate signed off. Sequence is enforced by process, not by trust.

Why this model

Teams that adopt AI tools without changing their process see 10–20% productivity gains — real, but not transformational. This model targets 3–5× throughput on greenfield features by shifting the constraint from writing code to writing context. The expensive thinking happens once, in a structured document. AI then executes against that document many times.

What changes for engineers

  • Stories are replaced by Product Functions (end-to-end capability slices)
  • Code writing is preceded by context assembly and design review
  • AI generates implementation; you validate it against the spec
  • Quality gates are automated and hard-blocking, not advisory
  • Reviews focus on intent and design, not syntax

Foundation

Product Function (PF)

The atomic unit of delivery in this model. A complete, independently deployable capability from the user's perspective — not a technical subtask.

✅ A Product Function IS

  • Independently testable end-to-end
  • Independently deployable (or feature-flaggable)
  • Traceable to a business outcome
  • Completable within one delivery iteration
  • Understood by the user, not just the team

❌ A Product Function is NOT

  • "Create auth controller" — technical subtask
  • "Add unit tests for user service" — QA-only task
  • "Refactor database layer" — internal rework
  • Any task spanning 3+ services and 2+ teams
  • A JIRA story decomposed from a subtask

Good vs Bad Examples

StatementPF?Reason
"User authenticates via SSO and receives a scoped JWT"✓ YESUser-centred, independently testable, clear outcome
"Implement Helm chart for auth service"✗ NOInfrastructure task; no user-facing outcome
"User receives email notification on failed login after 3 attempts"✓ YESComplete user journey, observable, deployable alone
"Add Redis caching to session store"✗ NOPerformance enhancement; not independently meaningful
"Admin can revoke a user's active session from the console"✓ YESAdmin user journey, testable, real outcome

Phase 0 · Pre-condition

Context Stack & FCD Assembly

Context is not a prompt — it is a structured, versioned package assembled before any AI generation begins. All three layers must be present before Phase 1 starts. Missing any layer is a gate failure.

📋

Layer 1 — Requirement Context

Sources: Jira epic/story, Confluence specs, product research, design artefacts, stakeholder decisions

  • Problem statement (user-centred, one paragraph)
  • Acceptance criteria — numbered, independently verifiable
  • Explicit non-goals
  • Edge cases and failure scenarios known at requirements stage
  • Jira/Confluence links for traceability
  • Data sensitivity classification (PII / Financial / Internal / Public)
⚙️

Layer 2 — Technical Context

Sources: ADRs, NFR catalogue, team learning docs, security guidelines, anti-pattern register

  • Applicable architecture patterns (event-driven, CQRS, REST-first…)
  • NFR targets: latency p95/p99, throughput, availability SLA
  • Security: auth model, encryption at rest/transit, secrets handling
  • Anti-pattern register entries relevant to this PF (injected into every prompt)
  • Team conventions: naming, folder structure, error handling, dependency rules
💻

Layer 3 — Code Context

Sources: Existing service interfaces, shared libraries, DB schema, test examples, pipeline templates

  • Interface contracts (API signatures, message schemas)
  • Database entity models for affected domains
  • Shared utility patterns in use (error wrapper, logging initialiser…)
  • 1–2 representative unit test files showing team test style
  • CI/CD pipeline template reference
📌
Always inject: "All generated code must follow these patterns exactly for naming, error handling, logging, and structure. Do not introduce new patterns not present in the examples."
Example FCD — PF-042 Enterprise SSO with Scoped JWT
# FCD: Enterprise SSO with Scoped JWT PF-ID: PF-042 | Version: 1.0 | Owner: Priya S. (Tech Lead) Status: Approved ## REQUIREMENT CONTEXT Problem: Dev teams authenticate to internal APIs using per-service credentials stored in .env files. This creates N credential rotation cycles, onboarding friction, and audit gaps. Goal: single SSO login → scoped JWT → all APIs accept. Acceptance Criteria: [AC-01] User authenticates via Okta OIDC and receives a JWT (RS256) valid 15 min [AC-02] JWT contains scoped claims mapped from AD group memberships [AC-03] Protected endpoints reject expired JWTs with 401 + WWW-Authenticate [AC-04] Invalid Okta token returns 401 within 200ms (no upstream call) [AC-05] Okta timeout (>3s) returns 503 with Retry-After: 30 header Non-goals: Social login (Google/GitHub), mobile app SSO, MFA changes Data classification: Auth tokens = Confidential; user.email = PII ## TECHNICAL CONTEXT Architecture pattern: REST API + async audit event on auth success NFR: p95 < 150ms (token validation path), p99 < 400ms, availability 99.9% Security: RS256 signing only (no HS256); public key rotated every 30 days Anti-patterns in scope: [AP-007] No secrets in env vars — use AWS Secrets Manager [AP-001] No sync HTTP between internal services for auth validation ## CODE CONTEXT Interface: JwtService.createToken(claims: ClaimSet, expirySeconds: int): Token DB schema: users(id, okta_sub, email, ad_groups[], last_login) Test style: [see auth-service/src/test/AuthControllerTest.java for pattern] Config schema: auth.jwt.signing-key-arn, auth.jwt.expiry-seconds, auth.okta.domain

💡 The Handoff Rule

Opus drives every phase that produces a gate artefact (plan, HLD, LLD, security report). Sonnet executes every phase that consumes an approved gate artefact (code, tests, scenarios). The model boundary follows the gate boundary.

📊
Cost ratio: ~20% Opus (reasoning phases) · ~80% Sonnet (generation phases). Most tokens should be cheap because expensive thinking happened once in a structured, reusable context document.
Gate Artefact

Tech Spec Standard

The bridge between requirements and implementation. AI-assisted but human-approved before any code generation begins. A missing or ambiguous section is a gate failure.

Required Sections

#SectionWhat it must containWhy it matters
4.1Functional ScopeComponent boundary map; data flow diagramDefines blast radius — what can and cannot change
4.2Architecture DecisionSelected pattern + rationale; rejected alternatives (1 sentence each); ADR refPrevents AI from silently choosing a different pattern
4.3NFR Targets BINDINGLatency p95/p99, availability, error rate, throughput — with measurement methodNFR violations are spec-level failures, not code review comments
4.4Interface ContractOpenAPI fragment or message schema; input validation; error responses; idempotencyAI generates to this contract — ambiguity = wrong API
4.5Data DesignSchema changes; migration strategy; retention rulesMigrations on live systems fail silently if not specified
4.6Security & ComplianceAuth scope; data classification; encryption; audit loggingSecurity omitted at spec level is security omitted in code
4.7Observability DesignNamed metrics (counter/gauge/histogram); log events with fields; trace spans; alert thresholdsFeatures without observability cannot be operated in production
4.8What Not To DoAnti-pattern register entries for this PF — injected verbatim into every AI promptGuardrails AI cannot infer without explicit instruction

Phase 5 · Automated

Quality Gates

Five deterministic checks run in CI on every commit. All are hard blocks — the pipeline fails on any violation. Not advisory. Not warnings. Hard stops.

🔴
Zero-tolerance policy: Any gate that fails blocks the entire pipeline. There is no "merge and fix later." Fix the violation, push again, wait for CI.
1

Linting HARD BLOCK

ESLint / Checkstyle / Pylint at maximum project-defined ruleset. Zero warnings tolerated — warnings are treated as errors in CI config. Formatter check (Prettier / Black) — format violations block pipeline. Import order and unused import checks.

💡
Run linting locally before committing. A clean local lint run is part of the Phase 4 post-generation checklist.
2

CodeRabbit Automated Review MEDIUM+ BLOCK

Triggered automatically on every PR. Reviews for: code smells, complexity violations, missing error handling, performance anti-patterns, test coverage gaps, and naming inconsistencies.

Resolution rule: Any comment at severity Medium or above must be resolved OR explicitly acknowledged with a written rationale before merge. Low findings may be acknowledged without resolution. CodeRabbit summary is auto-appended to PR description.

3

Claude Security Review OPUS HIGH/CRITICAL BLOCK

Run as a CI step using the Appendix B.4 security prompt against the full diff. Covers: injection risks, broken auth, sensitive data exposure, security misconfiguration, insecure dependencies, secrets in code, input validation gaps.

SeverityGate action
Critical / HighPipeline fails — fix required before merge
MediumEngineer provides written disposition (fix / accept risk with rationale)
Low / InfoLogged; no action required for merge

Output is appended to the PR as a comment for audit trail. See Prompt Library for the exact prompt.

4

Unit Test Coverage ≥80% BLOCK

Coverage report generated on every CI run. New code must have ≥80% line coverage. Coverage delta tracked: no PR may reduce coverage below the current baseline. Coverage is measured on new code only — legacy coverage debt does not block new PFs.

5

Dependency Scan CRITICAL CVE BLOCK

OWASP dependency check or Snyk runs on every PR. Zero known critical CVEs allowed in new or updated dependencies. High CVEs require accepted risk documentation or a fix within the PR.

💡
When AI generates a import [new-library] you haven't used before, run the dependency scan locally before pushing. New AI-suggested dependencies are a common source of CVE findings.
Environment Promotion

Definition of Readiness

DoR governs promotion between environments. Distinct from DoD (which governs PR merge). A feature can pass DoD but fail DoR if environment-specific conditions are not met.

DoR: Lower → QA

DoR: QA → Pre-Production

DoR: Pre-Production → Production

When Things Block

Escalation Paths

The gate model is clear when things go right. These paths govern what happens when they don't. Every blocked scenario has a named resolution route and a time limit.

🔴 Trigger
FCD Cannot Complete — Requirements Missing or Contradictory

Phase 0 cannot proceed because Jira/Confluence content is missing, ambiguous, or contradictory.

  1. Engineer flags to tech lead within 4 hours of starting FCD assembly
  2. Tech lead contacts product owner with a specific list of missing items (not "unclear requirements")
  3. Product owner has 1 business day to resolve or schedule a clarification session
  4. If unresolved: delivery manager escalates to programme lead
  5. PF does not proceed to Phase 1 until FCD is signed off — no exceptions
🔁 Trigger
Gate Rejection Loop — Same Gate Fails More Than Twice

This is a process signal, not an engineer performance signal. Two rejections mean either the gate criteria are ambiguous or the engineer has not been adequately coached on the model.

  1. On third rejection: tech lead pairs with the engineer to complete the gate artefact — not a review, a working session
  2. Tech lead documents what was missing or misunderstood
  3. If template ambiguity: update FCD template or DoD checklist
  4. If capability gap: schedule targeted coaching before next PF
🔐 Trigger
Security Finding with Ambiguous Severity

Claude Security Review produces a finding where correct severity is genuinely debatable.

  1. Engineer proposes disposition with written rationale within 24 hours
  2. Security engineer confirms or corrects disposition within 48 hours
  3. If security engineer and tech lead disagree: engineering lead makes final call and documents it
  4. Finding + disposition recorded in PR comment permanently — never silently closed
⚡ Trigger — Declared by Engineering Lead Only
Critical Hotfix — Abbreviated Process

Production defect or security vulnerability requiring a fix that cannot wait for the full lifecycle.

⚠️

🌱 Trigger
Greenfield Context — No Existing Codebase
  1. Tech lead selects the closest analogous service as code context source
  2. If no analogous service exists: team defines patterns explicitly in FCD Code Context before any generation
  3. First PF on a greenfield service: tech lead must pair with engineer for Phase 4 — the generated output sets the pattern baseline
  4. After first PF merges: patterns immediately added to shared context baseline

Transformation

Adoption Ramp-Up

This guideline does not activate by being published. Transformation requires a staged adoption sequence. Skipping stages produces nominal compliance but practical reversion within two sprints.

⚡ AI Literacy Prerequisites

Before a developer works their first PF under this model, they must demonstrate ability to:

SkillHow to verify
Write a structured prompt with context injection and hard constraintsComplete a prompt workshop exercise
Read AI-generated code critically — identify hallucinations and pattern violationsReview a seeded hallucination exercise
Assemble a small FCD from a given Jira + Confluence specFCD peer review exercise
Know the Opus vs Sonnet split for their tasksModel selection quiz (5 questions)
⚠️
If the team lacks this baseline, a half-day AI literacy workshop precedes Stage 1. Starting Stage 1 without it wastes the pilot and erodes confidence in the model.
1

Pilot

Weeks 1–2

Who: One senior engineer + tech lead, working together. What: One low-risk, well-understood PF — an enhancement, not a new domain.

  • Tech lead assembles the FCD; engineer reviews it (inverted for learning)
  • Both attend every phase review together
  • After completion: 30-min debrief — what worked, what was awkward, what was missing
  • Update FCD template and Appendix B prompts from findings before Stage 2
🎯
Goal: Complete the full lifecycle end-to-end. Surface every friction point. Validate the gate sequence.
2

Expansion

Weeks 3–4

Who: Two engineers independently, tech lead reviewing both. What: Two concurrent PFs of moderate complexity.

  • Each engineer assembles their own FCD independently
  • Tech lead reviews both FCDs in a shared 30-min session — surface inconsistencies
  • Any hallucination or gate rejection reviewed as a team learning, not an individual failure
🎯
Goal: Validate the model works without tech lead co-piloting. Identify coaching gaps.
3

Full Team Adoption

Month 2

Who: Entire team. What: All new PFs follow the model. In-flight work under old process continues until complete.

  • Introduce DoR gates for the first time
  • Begin tracking process metrics from this point
  • Hold the first formal retrospective using the continuous improvement cycle
  • Update shared context baseline with patterns from Stages 1–2
🎯
Goal: Model is the default, not the exception. Metrics baseline established.
4

Optimisation

Month 3+

Who: Entire team with engineering lead visibility. What: Model is stable; focus shifts to efficiency and measurement.

  • Process metrics reviewed every sprint retrospective
  • Anti-pattern register actively maintained
  • Prompt library expanded from team-specific learnings
  • Engineering lead assesses transformation progress against Five-Index baseline
🏁
Adoption is complete when: Context reuse rate >60%, AI rework rate <20%, defect escape rate <5% — sustained over three consecutive sprints.

B.4 — Claude Security Review

OPUSv1.1 · Run in CI at Phase 5
You are a security engineer reviewing a code diff. Analyse the following changes for security vulnerabilities.

Check for ALL of the following:
- Injection risks (SQL, command, template, header injection)
- Broken or missing authentication/authorisation
- Sensitive data exposure (logging PII, unencrypted storage, unsafe serialisation)
- Security misconfiguration (CORS, security headers, TLS settings, error messages)
- Insecure dependencies (flag any new dependency for manual CVE check)
- Hardcoded secrets or credentials (including in comments and test files)
- Missing input validation on any external input
- Insecure direct object references or path traversal risks

For each finding provide:
- Severity: Critical / High / Medium / Low / Informational
- Location: file name and line number
- Description: what the vulnerability is and how it could be exploited
- Remediation: the specific fix required

Final line (required): "Security gate: PASS / FAIL — [N] findings above Medium severity"

Failure Modes

Anti-Patterns

These are the failure modes that erode the model's value. Each has been observed in teams adopting context-first delivery. Treat them as hard rules, not suggestions. Click to expand.

📌
The anti-pattern register is a living document. New entries are added after every incident retrospective. Tech leads own it. A register last updated 6 months ago is documentation theatre — see AP-M-007.
AP-M-001Thin context, fast generation
Skipping FCD assembly to start coding faster. The instinct is understandable — writing context feels like overhead before "real work." But AI generation on thin context produces technically plausible but functionally wrong code. The review, rework, and re-test cycle costs 2–4× the time saved on context assembly. The FCD is not overhead — it is the product specification.
AP-M-002Context as a one-time document
Writing the FCD at the start of a PF and never updating it as requirements evolve or design decisions change. AI generation on stale context produces confidently wrong output — it will generate code that was correct for the original requirement but not the current one. The FCD must be treated as the source of truth throughout the delivery cycle. When requirements change, update the FCD before regenerating anything.
AP-M-003AI review replacing human review
Using CodeRabbit and Claude Security Review as the only review mechanism — skipping the tech lead review because "the AI already checked it." Automated tools catch structural, pattern, and security issues. They do not catch design intent misalignment, business logic errors, or strategic mistakes. A senior engineer reviewing a PR is doing something qualitatively different from an AI tool. Both are required.
AP-M-004Merging without full test gate
Merging a PR after all human approvals when CI is still running. "It'll pass — just let it catch up." This breaks the sequence guarantee that is the foundation of the model. If tests fail after merge, the main branch is broken, every other engineer's work is blocked, and you've lost the context to fix it quickly. Tests must be green before merge. This is enforced via branch protection — it is not negotiable.
AP-M-005Product Function too large
A PF that spans multiple services, multiple data domains, and multiple teams is not a PF — it is a programme. This model works because a PF fits within one team's context and one iteration's scope. When a PF is too large, the FCD becomes unmanageably large, the AI generation produces code for parts of the system it doesn't have enough context for, and the gate sequence becomes impractical. Decompose before context assembly begins.
AP-M-006Skipping observability wiring
Treating metrics, structured logging, and distributed tracing as post-delivery cleanup tasks. "We'll add monitoring in the next sprint." Features that cannot be measured in production are not complete — they are deployed blind. When something fails in production, you have no data to debug it. Observability is specified in the Tech Spec (section 4.7) and is part of DoD. It is generated alongside the code, not added later.
AP-M-007Anti-pattern register not maintained
The register only works if it is updated continuously. An anti-pattern discovered in a post-incident review but not added to the register will be repeated by the next engineer who works in the same area. Tech leads own the register and update it as part of every retrospective. A register last updated six months ago is documentation theatre — it gives the appearance of governance without the substance.
AP-M-008Sensitive data in AI prompts
Code context assembled from real test fixtures, integration configs, or legacy code often contains real credentials, user data, or client-identifying information. Sending this to an external AI API is a data breach risk regardless of the provider's stated data handling policies. Sanitisation is mandatory before context assembly. The tech lead is accountable for confirming sanitisation before Phase 0 sign-off. For regulated industries, this must be validated against the client contract.
AP-M-009Prompt drift without governance
Engineers customise Appendix B prompts informally — adding instructions for their PF, removing constraints they find annoying, adjusting tone — without versioning or tech lead approval. Over time, different engineers use materially different prompts for the same task, producing inconsistent output quality and making team-wide debugging impossible. Prompt changes must go through the same review process as code changes. The Prompt Performance Log (Appendix D) is the governance mechanism.
AP-M-010Patching hallucinations instead of improving context
When AI generates a hallucinated method call or non-existent class reference, the instinct is to fix the individual lines and move on. This treats the symptom. Hallucinations are a context signal: the AI lacked information it needed to generate correctly. The correct response is to identify what was missing (usually a Code Context gap), add it to the FCD, and regenerate the module. Teams that patch without improving context see the same hallucinations on the next PF touching the same domain.
AP-M-011Isolated FCD assembly with no shared baseline
Every PF builds its technical context from scratch because no team-level baseline exists. Anti-patterns are discovered repeatedly. Code examples are inconsistently chosen. NFR targets vary without justification. This is the compounding-return failure mode — each PF should build on prior PFs' learnings. Maintaining the shared context baseline is not overhead: it is the mechanism by which the team gets smarter with each delivery. Target: >60% context reuse rate within three months.
