Executive Framing (One-Page TL;DR)

AI agents shift software from a request-response model to a goal-execution model. The model provides probabilistic intelligence; the harness converts that intelligence into controlled, observable, and commercially viable software behaviour. As models become more capable and more interchangeable, durable engineering value migrates into the harness: its context model, execution controls, state model, tool contracts, evaluation assets, recovery mechanisms, and accumulated operational knowledge.

This specification defines what an enterprise-grade or ISV-grade harness must contain, how it should be engineered, how it should be evaluated, and how it should be adopted. It is platform-agnostic and framework-agnostic. It is designed to complement the Cybage AI-Native SDLC Blueprint v1.1 and the Five-Index Measurement Framework (Adoption → Utilization → Quality → Velocity → Outcome).

The central engineering thesis:

The durable value of an agentic product will increasingly reside in the harness — not in the model. Organisations that industrialise harness engineering will convert changing model capability into reliable, differentiated, and governable software outcomes.

The specification is organised as a five-part narrative — Why → What → How → Prove → Adopt — followed by six appendices, including an authoritative HTML rendering directive (Appendix D) that governs how this document is published as an interactive single-file HTML deliverable.

PART I — WHY

Part I TL;DR

Agentic software makes execution paths probabilistic, natural language part of the control surface, and every step a potential state change. Traditional application scaffolding — REST controllers, cron jobs, workflow engines — cannot enforce the safety, reversibility, and evidence properties agentic work demands. Enterprises need a shared harness to industrialise adoption; ISVs need one to build a competitive moat; service providers need one to deliver managed agentic outcomes at scale. Ignoring the harness layer is the single most common cause of stalled agent pilots.

1. Executive Summary

AI agents are moving software systems from a request-response model to a goal-execution model. In a request-response system, software receives a defined input, executes predetermined logic, and returns a bounded output. In an agentic system, a model interprets intent, selects tools, changes state, generates or modifies code, reacts to failures, and may continue operating across multiple steps or sessions.

This shift makes the agent harness a critical software engineering layer.

A harness is the controlled runtime and engineering environment in which an AI agent operates. It determines:

  • what the agent can see;
  • which tools it can invoke;
  • how it plans and executes work;
  • how state and memory are maintained;
  • where code and commands run;
  • how permissions are granted;
  • how failures are recovered;
  • how actions are observed and audited;
  • how cost, latency, quality, and risk are controlled;
  • how humans intervene;
  • and how the system is tested, released, and improved.

The model provides probabilistic intelligence. The harness converts that intelligence into controlled software behaviour.

The central engineering thesis of this specification is:

The durable value of an agentic product will increasingly reside in the harness: its context model, execution controls, state model, tool contracts, evaluation assets, recovery mechanisms, and accumulated operational knowledge.

Open-source systems such as Pi, LangGraph, smolagents, and other agent runtimes demonstrate different architectural directions:

  • Pi emphasises a small terminal-native core extended through TypeScript modules, skills, prompt templates, packages, and custom providers.
  • LangGraph emphasises explicit stateful graphs, cyclic execution, persistence, interrupts, fault recovery, and human-in-the-loop workflows.
  • smolagents emphasises a minimal Python agent abstraction and code-first tool execution, including sandbox integrations.
  • Deep-agent and autonomous-worker approaches emphasise long-running work, planning, delegation, and durable execution.

These tools are useful foundations, but an enterprise or ISV-grade harness requires substantially more than selecting a framework. It requires a coherent platform architecture, software engineering standards, security controls, product design, test strategy, observability, governance, and an operating model.

This document defines those requirements.

1.1 Purpose

This specification establishes a reusable standard for designing, building, testing, deploying, operating, and evolving AI agent harnesses. It supports four practical outcomes:

  1. Build agentic software safely. Convert model capabilities into controlled, observable, repeatable business operations.
  2. Create reusable engineering assets. Avoid rebuilding tool integration, state, permissions, sandboxing, evaluation, and telemetry for every agent.
  3. Enable enterprise and ISV adoption. Meet requirements for security, tenancy, compliance, extensibility, reliability, and product lifecycle management.
  4. Standardise AI-assisted software delivery. Define how any AI coding tool should generate, change, test, validate, and document code, APIs, services, and HTML applications.

1.2 Scope

In scope: agent runtime architecture; framework-versus-harness responsibilities; model abstraction and routing; context engineering; state, memory, and persistence; tool and action design; workflow orchestration; planning and execution loops; sandboxing and isolation; policy and permission enforcement; identity, secrets, and tenancy; human approval and exception handling; reliability, recovery, and idempotency; observability and auditability; evaluation and regression testing; code generation and repository modification; HTML and frontend generation; CI/CD and release controls; enterprise and ISV product requirements; platform operating model; short-term and long-term business impact; reference patterns, anti-patterns, and examples; build-versus-buy decisions; maturity model and implementation roadmap.

Out of scope: training foundation models; designing model architectures; GPU infrastructure for model pre-training; generic chatbot UX without agent execution; business-domain rules unique to one industry; detailed legal interpretation for a specific jurisdiction; vendor procurement terms.

2. The Shift: Request-Response → Goal-Execution

Traditional software engineering assumes application logic is authored directly in code. Agentic software introduces a second form of runtime logic: model-generated decisions. This changes the engineering problem in five ways.

2.1 Execution paths become probabilistic

Two runs with similar input may select different tools, create different plans, or produce different intermediate artifacts. The harness must constrain this variability and measure whether it remains within acceptable bounds.

2.2 Context becomes executable configuration

Repository files, system instructions, policies, task history, memory, examples, and tool descriptions influence runtime behaviour. Context therefore requires versioning, testing, review, and release management (see §10.4).

2.3 Natural language becomes part of the control surface

Prompts and instructions can change system behaviour, but they are weaker than code-based enforcement. Harness engineering must determine what belongs in natural language and what must remain in deterministic controls (see §6.3, §16.1).

2.4 Agents modify their environment

An agent may change code, configuration, infrastructure definitions, databases, tickets, customer records, or deployment state. This demands transactional thinking, permissions, sandboxing, evidence, and rollback (see Ch 15, Ch 17, Ch 18).

2.5 Long-running work needs durable coordination

Tasks may pause for external systems, human approval, retries, model handoffs, or scheduled continuation. A production harness must support durable state and resumable execution rather than relying on one in-memory chat session (see §10.6, §19.2).

Harness engineering therefore combines: distributed systems; workflow engines; secure software execution; platform engineering; developer experience; AI engineering; quality engineering; SRE; product architecture; policy engineering; and human-computer interaction.

2.6 The coupling tension: model-coupled versus model-decoupled harnesses

A strategic fork has opened in how harnesses relate to the models they run. Two opposing approaches now compete for the same layer of the stack.

Model-coupled harnesses. Some harnesses are trained, via reinforcement learning, alongside a specific model family, so that the model becomes self-aware of the harness it runs inside — it learns the exact tool-call conventions, file-edit parameters, and context-management behaviour that harness expects. This coupling measurably improves tool-selection accuracy and task completion: swapping the underlying model for a different provider's model of comparable general capability degrades performance, because the fine-tuned familiarity with the harness's specific conventions is lost. This is a real and growing engineering advantage, not merely a vendor lock-in tactic — but it is still a lock-in, whichever way it is framed.

Model-decoupled harnesses. Other harnesses are deliberately built model-agnostic — favouring an open standard for tool-calling and context that does not depend on any one model provider. The stated rationale is direct: business continuity should not depend on the availability, pricing, or regulatory status of a single model provider (this restates the governing principle in §6.1, the model is not the system, from an adoption-risk rather than a purely architectural angle).

Why this matters for the build/buy/compose decision (Ch 27). As of mid-2026 this tension is unresolved industry-wide, and there is no single correct answer:

  • Coupled harnesses currently win on raw task performance for the specific model they are tuned against.
  • Decoupled harnesses win on portability, negotiating leverage, and resilience to supply-chain risk — including the very real scenario in which a specific model is restricted or banned for regulatory or export-control reasons mid-contract (see §18.6, Supply-chain controls).
  • An organisation building a harness should make this trade-off an explicit, named decision (see §31, Key Strategic Decisions) rather than an implicit consequence of which vendor's quickstart was easiest to adopt.

3. Market Need

3.1 Enterprise market

Enterprises need harness engineering because they cannot safely scale isolated agent experiments into core operations without a shared control layer.

Key enterprise needs include: central identity and access control; data residency and privacy controls; audit and traceability; approval workflows; separation of duties; policy enforcement; model-provider governance; usage and cost management; integration with existing systems; reusable domain tools; resilience and operational support; vendor portability; compliance evidence; controlled citizen development; and consistent engineering standards.

Without a common harness, departments create disconnected agents with incompatible tool definitions, weak security, duplicated infrastructure, inconsistent logs, and no common method to assess quality.

The enterprise value of a harness is therefore not merely faster development. It is controlled reuse.

3.2 ISV market

ISVs need harness engineering for a different reason: the harness becomes part of the product architecture and competitive moat.

An ISV-grade harness must support: multi-tenancy; tenant-specific policies and tools; customer-configurable workflows; model choice and regional deployment; extension marketplaces or plugin systems; safe customisation; versioned behaviour; metering and billing; customer-visible evidence; service-level objectives; product analytics; backward compatibility; and controlled feature rollout.

For ISVs, the harness determines whether agentic capabilities remain a collection of demos or become a scalable product line.

3.3 Technology service providers

Technology service providers can create a differentiated offering around harness engineering by combining: agent platform architecture; reusable accelerators; secure execution environments; domain-specific tools and skills; migration of existing workflows into agentic patterns; evaluation engineering; operational governance; and managed harness operations.

The service opportunity is not limited to building agents. It includes modernising the client's software platform so agents can act through stable, machine-readable interfaces.

3.4 The local-to-fleet migration path

Most agent deployments today begin as a process running on a single developer's laptop or workstation — a terminal-native coding harness, a personal assistant, or a single research loop. This is a materially simpler engineering problem than what most organisations are actually migrating toward: agents that run disconnected from any individual's machine, executing in cloud compute the organisation controls, invoking arbitrary tools and remote skills, and operating as part of a fleet rather than a single instance.

This local-to-fleet migration changes the problem in three concrete ways:

  1. Scale becomes unconstrained by a laptop's presence. Once an agent no longer depends on a person keeping a machine open, the only practical ceiling on execution volume is cost — there is no architectural reason a fleet could not run many thousands of concurrent agent executions per hour. Enterprises should expect adoption to look flat for a period and then increase sharply once this threshold is crossed, not gradually.
  2. Durability stops being optional. A single local process failing is an inconvenience the user restarts. A fleet-scale failure — a worker crashing mid-task, a network partition, a dependent service timing out — must be recovered automatically, because there is no human sitting in front of that specific execution to notice and retry it (see §15.16, new in this version, and §19).
  3. The platform-investment argument sharpens. As in the earlier MLOps cycle, the organisations that invest early in an internal platform for running these workloads at scale gain a compounding advantage: the platform itself becomes a source of institutional knowledge about what actually works for that organisation's specific workloads, independent of which vendor's demo looked best. This reinforces §3.1's framing of the enterprise harness value as controlled reuse, not merely faster initial development.

Organisations should treat "does this agent still need to run near a person's machine, or can it run disconnected in our own infrastructure" as an explicit checkpoint in the delivery roadmap (see Ch 28), because the infrastructure, durability, and observability requirements differ materially on either side of that line.

4. Short-, Medium-, and Long-Term Impact

4.1 Short-term impact: 0–18 months

Engineering impact. More code will be generated, making review, test, and integration the limiting constraints. Teams will standardise repository instructions, tool contracts, coding rules, and evaluation suites. Local and CI-based coding agents will become normal contributors to pull requests. Sandboxed execution and approval gates will be introduced around write operations. Platform teams will create common model gateways, agent telemetry, and secret brokering. Existing workflow engines will be combined with model-driven decision nodes. Quality engineering will shift from testing only the final application to testing agent trajectories and tool choices.

Organisational impact. AI platform teams will emerge beside cloud and data platform teams. Security teams will define agent identities and machine-action policies. Product managers will specify agent boundaries, escalation rules, evidence, and autonomy levels. Software developers will spend more time on architecture, contracts, tests, and validation than on routine code production.

Commercial impact. Buyers will ask vendors for measurable agent reliability, auditability, and cost controls. Open-source frameworks will reduce initial build cost, but production hardening will remain substantial. Pricing may split between model consumption, agent runtime, managed execution, and outcome-based charges.

4.2 Medium-term impact: 18–36 months

Harnesses will become shared enterprise platforms rather than project-specific libraries. Agent behaviour will be versioned and released like software. Domain-specific agent stores, tool catalogs, policy packs, and evaluation packs will emerge. Software systems will expose agent-optimised APIs, metadata, and action semantics. Agents will coordinate across SDLC stages: planning, coding, testing, security, deployment, and operations. Product telemetry will measure not only clicks and API calls but delegated goals, autonomous completion, intervention rate, and evidence quality. Platform vendors will compete on durable execution, sandboxing, observability, interoperability, and governance.

4.3 Long-term impact: 3–7 years

The harness may become the primary application runtime for knowledge work and software operations. Many user journeys will be expressed as goals rather than screens and workflows. Software products will need both human-facing and agent-facing interaction layers. Application architecture will increasingly separate intent, policy, planning, execution, and evidence. The most valuable engineering assets may become tool contracts, verified workflows, domain memory, policy models, and evaluation corpora. Software engineers will design environments in which agents can safely construct or adapt solutions, rather than coding every execution path directly. Harness changes may alter product behaviour as materially as application code changes, requiring equivalent governance.

PART II — WHAT

Part II TL;DR

A harness is not a framework. A framework answers "how do I define an agent?" A harness answers "where does execution occur, what is permitted, what state persists, how is every action traced, and how are quality/risk/cost measured?" Ten governing principles anchor design: the model is not the system; the harness owns control; determinism where it matters; every action attributable; generated output untrusted until verified; least privilege; reversibility; explicit state; evaluation as product; evolvability. Autonomy is earned through evidence, not granted by model capability — the A0–A5 ladder makes this explicit.

5. Definitions

5.1 Agent

A software actor that uses a model to interpret a goal, decide or select actions, invoke tools, observe outcomes, update state, and continue until a completion, escalation, or termination condition is reached.

5.2 Agent framework

A development abstraction used to define agent behaviour, such as prompts, graph nodes, tool schemas, model calls, messages, or routing logic. A framework typically answers: How is an agent defined? How are tools registered? How are steps linked? How is a model called? How is state represented in application code?

5.3 Agent harness

The concrete runtime, control plane, execution plane, and engineering environment in which an agent operates. A harness answers: Where does execution occur? What is permitted? What context is supplied? What state persists? How is every action traced? How are errors retried or compensated? How is a task paused, resumed, cancelled, or rewound? How are quality, risk, and cost measured? How are changes promoted to production?

5.4 Agent platform

A productised collection of harness services, developer tooling, operations tooling, governance, deployment capabilities, and reusable components used to build and run multiple agents.

5.5 Tool

A typed, bounded capability exposed to an agent. Examples include reading a file, querying a database, creating a pull request, running a test, searching a knowledge base, or invoking a business API.

5.6 Skill

A reusable package of instructions, examples, tool usage guidance, domain conventions, and optional executable resources that enables an agent to perform a specific class of tasks.

5.7 Workflow

A defined sequence or graph of states and actions, including branches, loops, gates, retries, approvals, and terminal conditions.

5.8 Sandbox

An isolated execution environment that limits filesystem, process, network, identity, and resource access for generated code or agent actions.

5.9 Context engineering

The design of what information, instructions, tools, examples, policies, state, memory, and environmental observations are made available to a model at each step.

5.10 Evidence

Machine-generated proof of an agent action or result, such as logs, diffs, command output, test results, screenshots, API responses, approvals, traces, checksums, or signed artifacts.

(Extended glossary — including Cybage-specific terms HIL, CoE, L1–L5, T1/T2/T3, RAG, MCP, DART-PEM, ISV, SI — appears in Appendix F.)

6. Governing Principles

6.1 The model is not the system

The model is one replaceable reasoning component. Business continuity, safety, and product differentiation must not depend entirely on a single model or provider.

6.2 The harness owns control

The harness, not the prompt, must enforce permissions, data boundaries, budgets, timeouts, approvals, and termination conditions.

6.3 Code must remain deterministic where determinism is required

Use normal software for validation, calculations, policy enforcement, identity checks, data transformations, and transaction integrity. Use models where interpretation, synthesis, planning, or unstructured reasoning creates value.

6.4 Every consequential action must be attributable

The system must record who initiated the task, which agent and version ran, which model was used, which tools were invoked, what changed, which evidence was produced, and who approved the outcome.

6.5 Generated output is untrusted until verified

Agent-produced code, queries, plans, files, and decisions must pass appropriate static, dynamic, policy, and human checks before use.

6.6 Least privilege is the default

An agent receives only the minimum tools, data, credentials, network access, and execution time required for the current task.

6.7 Reversibility is a design requirement

Important actions must support preview, approval, rollback, compensation, branch isolation, versioning, or replay.

6.8 State must be explicit

Important state must not exist only inside a prompt or model conversation. It must be represented in typed, inspectable, versioned data structures.

6.9 Evaluation is part of the product

An agent cannot be considered production-ready without repeatable task suites, safety tests, quality thresholds, and regression detection.

6.10 The harness must be evolvable

Model providers, policies, workflows, tools, and evaluation criteria will change. Components must be replaceable behind stable contracts.

7.1 Selection principle

Do not select a framework by feature count. Select an architectural approach based on: task duration; action risk; workflow predictability; state complexity; required observability; execution environment; extension model; latency; tenant model; developer language; operational ownership; and acceptable vendor dependency.

7.2 Recommended positioning

Use a layered architecture in which:

  • the agent framework is replaceable;
  • the harness contracts are stable;
  • the tool catalog is product-owned;
  • the policy engine is external to the model;
  • the state store is durable and typed;
  • the sandbox is independently controlled;
  • and the evaluation system can replay tasks across model and harness versions.

7.3 Illustrative tool landscape (as of July 2026)

The six conceptual categories in §7 map onto a fast-moving, real market. The tables below are illustrative, not exhaustive, and are a point-in-time snapshot — tool names, maintainers, and status will change. Stateful orchestration frameworks (LangGraph's category): LangGraph (LangChain Inc.); CrewAI (CrewAI Inc.); Microsoft Agent Framework, the successor to AutoGen and Semantic Kernel (Microsoft); Google ADK (Google); LlamaIndex Workflows (LlamaIndex); DSPy (Stanford NLP); Temporal (Temporal Technologies); ZenML (ZenML GmbH), a five-year-old open-source MLOps workflow-orchestration engine now repositioned for agent workloads; Kitaru (ZenML), a durable-execution runtime and SDK/UI built on top of ZenML specifically to add checkpointing, replay, and cross-harness adapters (Anthropic Agents SDK, OpenAI Agents SDK) to any agent harness without requiring a rewrite.

Minimal code-first libraries (smolagents' category): smolagents (Hugging Face); OpenAI Agents SDK (OpenAI); PydanticAI (Pydantic); Vercel AI SDK (Vercel); Agno (Agno AI).

Managed enterprise runtimes: AWS Bedrock AgentCore; Microsoft Foundry Agent Service; Gemini Enterprise (Google Cloud); Salesforce Agentforce 360; IBM watsonx Orchestrate; Databricks Agent Bricks; Anthropic Managed Agents, model-provider-hosted routines and infrastructure built directly into the harness layer, illustrating the model-coupled path described in §2.6.

Open, commoditizing foundation models (relevant to the build/buy/compose economics in Ch 27, not a harness category in its own right): open-weight models such as GLM (Zhipu AI), Kimi (Moonshot AI), MiniMax, and Mistral have closed much of the capability gap with proprietary frontier models — one widely cited mid-2026 comparison put a recent open model at roughly 95% of a leading proprietary model's benchmark performance. As this gap narrows, the commercial argument in §1 and §32 sharpens further: if the model increasingly behaves like a commodity input, competitive differentiation and durable value continue to migrate toward the harness, the runtime, and the accumulated operational knowledge built around it — not toward which model is called.

Sandboxing and execution isolation (underlying §10.8): E2B, Modal, Daytona, Cloudflare Sandbox SDK, Fly.io Machines — most build on gVisor or Firecracker.

Evaluation and observability (underlying Ch 20–21): LangSmith, Langfuse (now part of ClickHouse), Braintrust, W&B Weave, Arize Phoenix, TruLens (now maintained by Snowflake).

Open standards and protocols. The most consequential trend for harness engineering through 2025–2026 is standards convergence: MCP, A2A (Agent2Agent), and AGNTCY have each moved to multi-vendor Linux Foundation governance, with AWS, Google, Microsoft, Cisco, IBM, SAP, ServiceNow, and Salesforce co-governing. This is the clearest signal yet that tool-calling and agent-to-agent interoperability are consolidating around shared, vendor-neutral contracts rather than fragmenting — directly reinforcing the governing principle in §6.1 (the model is not the system) and the recommended positioning in §7.2 (harness contracts should be stable and framework-independent).

A parallel consolidation is underway among frameworks themselves: Microsoft is folding both AutoGen and Semantic Kernel into Microsoft Agent Framework, and OpenAI's Assistants API is being retired in favour of the Responses API. Treat any framework choice as provisional and keep the harness contracts in §7.2 the stable layer, not the framework API surface.

8. Autonomy Levels (A0–A5)

Autonomy is earned through evidence, controls, and operating maturity — not granted by model capability. This scale is orthogonal to, and composable with, the Cybage L1–L5 maturity model (see Ch 30).

Level Description Permitted behaviour Typical use
A0 – Advisory Produces analysis or recommendation only No external side effects Strategy, review, explanation
A1 – Drafting Creates proposed artifacts in isolated storage No system-of-record change Code drafts, emails, plans, SQL drafts
A2 – Supervised action Executes actions after per-action approval Bounded writes with human confirmation Ticket updates, pull requests, test execution
A3 – Policy-bounded autonomy Executes approved classes of actions automatically Reversible actions within defined scope Dependency updates, non-production remediation
A4 – Monitored autonomy Runs long-lived workflows with exception-based supervision Significant but controlled operations Production operations with strong guardrails
A5 – Delegated authority Acts on business outcomes under formal authority High-impact actions Rare; requires mature controls and domain-specific governance

An agent should not be assigned a higher autonomy level merely because the model appears capable. Autonomy must be earned through evidence, controls, and operating maturity (see Ch 20 for the evaluation basis, Ch 22 for the production readiness gate).

PART III — HOW

Part III TL;DR

An enterprise-grade harness is a layered system: intake → control plane → runtime → tool plane + execution plane → state/evidence → observability. Each layer has explicit, versioned contracts. Tools are narrow, typed, and idempotent; state is typed and durable; sandboxes are deny-by-default; policy is external to the model; every consequential action produces evidence. AI-assisted coding and HTML generation are treated as production software — with mandatory inspect → plan → change → verify → evidence sequences. Design patterns (deterministic shell, plan-execute-verify, capability tokens, read-plan-write separation) are as important as component design. Twelve anti-patterns must be actively prevented.

9. Reference Architecture

10. Logical Components

10.1 Task intake service

The task intake service must transform a human or system request into a validated task contract.

A task contract should contain:

task_id: "uuid"
initiator:
  type: "human|system|agent"
  identity: "principal-id"
tenant_id: "tenant-id"
objective: "Required outcome"
inputs:
  references: []
constraints:
  deadline: null
  max_cost: 10.00
  max_steps: 50
  allowed_data_classes: ["internal"]
  allowed_environments: ["development"]
required_evidence:
  - "change_diff"
  - "test_results"
approval_policy: "engineering-standard"
completion_criteria:
  - "all_acceptance_tests_pass"

The task contract must be immutable once execution starts, except through a versioned amendment event.

10.2 Agent registry

The registry must store: agent identifier; purpose; owner; version; status; model policy; prompt/instruction version; workflow version; allowed tools; default budgets; risk class; required approvals; evaluation suite; supported tenant and environment scope; deployment history.

No agent version should execute in production unless it is registered and approved.

10.3 Model gateway

The model gateway must abstract provider-specific APIs and centralise: authentication; provider selection; model allowlists; failover; regional routing; token and cost accounting; rate limits; prompt and response logging policy; data-retention options; content filtering; caching where safe; model health and latency; model version pinning; structured output enforcement.

Model selection should be policy-based rather than embedded throughout business code.

Example routing policy:

routes:
  - task_class: "code_review"
    models: ["high-reasoning-primary", "high-reasoning-fallback"]
    max_input_tokens: 180000
    temperature: 0
  - task_class: "classification"
    models: ["small-low-latency"]
    max_cost_per_call: 0.01
  - task_class: "sensitive-data"
    providers: ["private-region-provider"]

10.4 Context assembler

The context assembler is responsible for producing the smallest sufficient context for each agent step.

It should combine: system and policy instructions; current task contract; active workflow state; relevant short-term history; selected long-term memory; repository or business knowledge; tool definitions; examples; environment observations; prior errors; cost and step budget; required output schema.

Context assembly must be traceable. The harness should record which sources were selected and why.

Context priority order. (1) Non-overridable safety and policy controls; (2) task contract and completion criteria; (3) current state and pending decision; (4) tool contracts and environment facts; (5) domain and repository knowledge; (6) relevant examples; (7) prior conversational history.

Context controls. Maximum token budget; source-level access control; relevance threshold; freshness requirements; deduplication; prompt-injection scanning; sensitive-data redaction; provenance metadata; compaction policy; conflict detection.

10.5 Planner and router

The planner determines the intended sequence or decomposition of work. The router chooses the next state, tool, model, sub-agent, approval, or terminal action.

Planning may be: fixed and deterministic; model-generated but validated; graph-based; hierarchical; event-driven; or hybrid.

High-risk tasks should use constrained or validated plans rather than unconstrained free-form planning.

A plan should include:

{
  "goal": "Implement accessible dark mode",
  "steps": [
    {
      "id": "inspect",
      "action": "repository.inspect",
      "expected_evidence": ["affected_files"]
    },
    {
      "id": "change",
      "action": "repository.patch",
      "depends_on": ["inspect"],
      "expected_evidence": ["diff"]
    },
    {
      "id": "validate",
      "action": "test.run",
      "depends_on": ["change"],
      "expected_evidence": ["test_report", "accessibility_report"]
    }
  ],
  "rollback": "discard_branch"
}

10.6 Workflow engine

The workflow engine must support: explicit states; conditional transitions; cycles; parallel steps; joins; retries; timeouts; scheduled waits; human interrupts; cancellation; compensation; child workflows; durable checkpoints; replay; versioned workflow definitions.

State transitions must be append-only events or otherwise reconstructable.

Dynamic graphs, not static DAGs. Earlier workflow orchestration (including the pipeline-orchestration systems this specification's patterns descend from) assumed the graph was known and compiled ahead of time: load data, preprocess, train, evaluate — a directed acyclic graph whose shape does not change at runtime. An agent's execution trace is also a graph — a sequence of LLM calls and tool calls, sometimes combined — but the shape of that graph is decided step by step, by the model, while it runs, and it routinely cycles back on itself (retry, repair, re-plan). The workflow engine must therefore support graphs that are unrolled dynamically at execution time rather than only graphs compiled in advance; this is a structural requirement, not a minor variation, and it is the specific engineering problem that separates an agent workflow engine from a traditional data-pipeline DAG engine.

Mid-flight version pinning. Long-running tasks create a scenario traditional request-response systems never had to resolve: if a task has been running for an extended period — hours, days, or longer — and the underlying agent, workflow, or prompt version is updated while that task is still in flight, which version should the remainder of the task use? The harness must resolve this deliberately, not by accident of deployment timing. The correct default, consistent with §6.8 (state must be explicit) and the agent registry's version binding (§10.2), is that an in-flight task remains pinned to the agent, workflow, and prompt versions that were active when it started, and only picks up a newer version on its next fresh invocation. Silently migrating a running task onto new logic mid-execution makes the task's behaviour unreproducible and its evidence trail meaningless — the harness cannot claim a run's evidence corresponds to a specific, auditable version if the version changed underneath it while it ran.

10.7 Tool registry

Every tool must have a machine-readable contract.

Minimum tool metadata:

name: "repository.apply_patch"
version: "2.1.0"
description: "Apply a validated patch to an isolated branch"
risk_level: "medium"
input_schema: {}
output_schema: {}
required_scopes:
  - "repo:write"
side_effects:
  - "source_code_change"
idempotency: "idempotency-key-supported"
timeout_seconds: 30
retry_policy: "safe-on-network-failure"
approval:
  required_when:
    - "target_branch == 'main'"
audit_fields:
  - "repository"
  - "branch"
  - "commit_sha"

Tool design requirements. Use narrow, purpose-specific tools. Validate all inputs against a schema. Return structured outputs. Distinguish read operations from write operations. Declare side effects. Support idempotency where possible. Define retry safety. Enforce authorization outside the model. Produce evidence. Avoid returning excessive unstructured content. Version breaking changes. Include simulated and test implementations.

10.8 Sandbox manager

The sandbox manager must provision isolated execution environments.

Supported isolation levels. Process isolation; container isolation; microVM isolation; virtual machine isolation; WebAssembly isolation; disposable cloud workspaces; isolated browser sessions.

Minimum controls. Ephemeral filesystem; read-only base image; mounted workspace with explicit permissions; CPU, memory, process, and storage quotas; execution timeout; network deny-by-default; destination allowlist; secret injection at runtime; secret masking; package installation policy; malware and artifact scanning; output size limits; command audit; environment teardown; artifact retention policy.

10.9 State and persistence layer

State must be separated into distinct classes.

  • Run state. The exact execution state of the current task, including current node, pending action, step count, budget, errors, and outputs.
  • Checkpoints. Recoverable snapshots used to resume, inspect, branch, or rewind execution.
  • Working memory. Short-lived information needed during the current task.
  • Long-term memory. Durable information that may influence future tasks, such as user preferences, repository conventions, or confirmed domain facts.
  • Knowledge. Curated, authoritative content retrieved by the agent but not written automatically into memory.
  • Evidence store. Immutable or tamper-evident records of actions, outputs, diffs, test reports, approvals, and decisions.
  • Artifact store. Generated files, code packages, reports, screenshots, logs, and build outputs.

Memory writes must be explicit, validated, attributable, scoped, and reversible. A model must not silently convert arbitrary conversation content into durable memory.

10.10 Policy engine

The policy engine must evaluate every consequential action.

Policy inputs. Initiator identity; tenant; agent version; task risk; data classification; environment; tool; requested arguments; estimated cost; target resource; time; prior actions; approval state; anomaly signals.

Policy outcomes. Allow; deny; allow with constraints; require approval; require additional evidence; substitute safer tool; reduce permissions; terminate task.

Policy rules must not be implemented only in prompts.

10.11 Human control service

Human-in-the-loop (HIL) should be designed as a first-class workflow state, not an exception.

Supported actions. Approve; reject; edit proposed inputs; provide missing information; choose among options; reduce or expand scope; resume; cancel; roll back; escalate.

Approval screens must show. Requested action; reason; affected resources; proposed change; risk classification; policy result; evidence; cost incurred and estimated remaining cost; rollback method.

10.12 Evidence service

The evidence service should normalise: prompts and model responses where retention is permitted; tool calls; command output; source diffs; test results; security scans; screenshots; browser traces; deployment results; approval records; external API receipts; generated documents; final completion rationale.

Evidence must have timestamps, run identifiers, step identifiers, checksums, provenance, and retention classification.

10.13 Observability service

Agent observability must cover more than conventional application telemetry.

Required dimensions. Task success; completion criteria met; step count; model calls; model latency; tool latency; token usage; cost; retries; loop detection; approval wait time; human intervention rate; tool-selection accuracy; policy denials; sandbox failures; hallucinated tool attempts; context size; context source utilisation; output validation failure; rollback rate; customer-visible error rate.

(Full metrics catalog appears in Ch 21.)

11. Execution Lifecycle

A standard harness run should follow this fourteen-step lifecycle.

  1. Authenticate and identify. Resolve the human, service, or external agent identity and tenant context.
  2. Validate task contract. Ensure the objective, inputs, constraints, completion criteria, and required evidence are present.
  3. Classify task and risk. Determine data sensitivity, action risk, autonomy level, environment, and policy requirements.
  4. Select agent and workflow version. Bind execution to immutable agent, policy, tool, workflow, prompt, and evaluation versions.
  5. Allocate capability grant. Issue a short-lived capability set containing only the allowed tools, data, network destinations, and environments.
  6. Create sandbox and state. Provision an isolated workspace and initialise durable run state.
  7. Assemble context. Retrieve only relevant, authorised, and fresh context.
  8. Plan or enter graph. Generate or load the execution plan and validate it against policy and task constraints.
  9. Execute one bounded step. The agent proposes an action. The harness validates and invokes the tool.
  10. Capture observation and evidence. Store tool outputs, state changes, cost, and artifacts.
  11. Evaluate continuation. Determine whether to continue, retry, repair, branch, request approval, escalate, or terminate.
  12. Verify completion. Run deterministic acceptance checks and required evaluators.
  13. Produce outcome package. Return result, evidence, limitations, residual risks, and recommended follow-up.
  14. Finalise and retain. Close the sandbox, revoke credentials, store permitted memory, apply retention policies, and update operational metrics.

12.3 API contracts

All service and tool APIs must: use versioned schemas; validate input and output; define error classes; define idempotency behaviour; propagate correlation identifiers; support deadlines and cancellation; avoid ambiguous free-form return values where structured data is possible; provide backward compatibility policy.

12.4 Typed state

Agent state should be represented in typed schemas.

export interface CodingRunState {
  taskId: string;
  phase: "inspect" | "plan" | "modify" | "test" | "review" | "complete";
  repository: {
    url: string;
    baseRevision: string;
    workingBranch: string;
  };
  affectedFiles: string[];
  plan?: ChangePlan;
  testResults: TestResult[];
  risks: RiskFinding[];
  budget: {
    maxSteps: number;
    usedSteps: number;
    maxCostUsd: number;
    usedCostUsd: number;
  };
}

Do not store critical run state only as chat messages.

12.5 Error taxonomy

The platform must distinguish: invalid task; policy denial; authentication failure; authorisation failure; unavailable model; malformed model output; hallucinated tool; invalid tool arguments; tool business error; transient integration failure; sandbox failure; timeout; budget exhausted; loop detected; output verification failure; human rejection; cancellation; irrecoverable state corruption.

Each error class must define retry, escalation, and evidence behaviour.

12.6 Idempotency and side effects

Every write tool must document whether it is: naturally idempotent; idempotent with a key; safe to retry before acknowledgement; unsafe to retry; compensatable; irreversible. The harness must not automatically retry unsafe operations.

12.7 Concurrency

State updates must use optimistic concurrency, version checks, leases, or workflow-engine guarantees to prevent duplicate or conflicting execution.

12.8 Configuration management

The following must be version-controlled: agent definitions; instructions; prompts; tool schemas; model routing rules; workflows; policy bundles; sandbox images; evaluation datasets; thresholds; UI approval templates. Production configuration changes must pass review and automated validation.

13. AI-Assisted Coding Specification

This chapter defines the minimum standard for using any AI tool to create or modify software.

13.1 Mandatory operating sequence

An AI coding agent must follow this sequence:

  1. Understand the task and acceptance criteria.
  2. Inspect the repository before proposing changes.
  3. Identify applicable instructions and architectural constraints.
  4. Establish a baseline by running relevant existing tests.
  5. Produce a bounded change plan.
  6. Modify only necessary files.
  7. Add or update tests.
  8. Run formatting, linting, type checks, unit tests, integration tests, and security checks as applicable.
  9. Inspect the final diff.
  10. Report evidence, limitations, and residual risks.

The agent must not claim successful completion without executing verification appropriate to the change.

13.2 Repository instructions

Every AI-enabled repository should include a concise machine-readable instruction hierarchy.

/AGENTS.md                 Global repository rules
/docs/architecture.md      Architectural boundaries and decisions
/docs/testing.md           Test strategy and commands
/docs/security.md          Security and data handling rules
/docs/ui-standards.md      Frontend and accessibility rules
/<module>/AGENTS.md        Module-specific instructions

Instructions should define: supported runtime and package manager; build and test commands; code style; architectural boundaries; prohibited dependencies; generated-file rules; security requirements; definition of done; required evidence.

13.3 Change planning

For non-trivial work, the agent must produce an internal or persisted plan containing: current behaviour; desired behaviour; affected components; proposed changes; test changes; migration concerns; compatibility risks; rollback approach. Plans must be revised when repository evidence contradicts assumptions.

13.4 Code quality requirements

Generated code must: be readable by a human engineer; follow existing project conventions; use clear naming; minimise unnecessary abstraction; avoid dead code; avoid placeholder implementations unless explicitly requested; handle errors deliberately; validate external input; separate business logic from infrastructure logic; avoid hard-coded credentials and environment values; include comments only where intent is not evident; preserve backward compatibility unless a breaking change is approved; include tests for changed behaviour.

13.5 Security requirements for generated code

The agent must check for: injection vulnerabilities; insecure deserialisation; path traversal; unsafe command execution; exposed secrets; broken authentication or authorisation; cross-tenant access; excessive permissions; dependency vulnerabilities; sensitive-data logging; insecure temporary files; unrestricted network calls; unsafe HTML rendering; missing CSRF or XSS controls where applicable.

13.6 Test requirements

At minimum, changed logic should have: positive-path tests; negative-path tests; boundary tests; error-handling tests; regression tests for the reported issue.

Where applicable, also require: contract tests; integration tests; browser tests; visual tests; accessibility tests; performance tests; security tests; migration tests; chaos or recovery tests.

13.7 Diff discipline

The agent must: keep changes scoped; avoid unrelated reformatting; preserve existing comments and behaviour unless intentionally changed; explain deleted logic; identify generated artifacts; avoid changing lockfiles unnecessarily; ensure the final diff corresponds to the task plan.

13.8 Completion evidence

A coding task is complete only when the outcome package includes:

summary: "What changed"
files_changed: []
tests:
  executed: []
  passed: []
  failed: []
quality_checks: []
security_checks: []
known_limitations: []
residual_risks: []
rollback: "How to revert"

14. HTML & Frontend Generation Specification

AI-generated HTML must be treated as production software, not visual mock-up output. This chapter governs both application HTML and the render of this specification itself (see Appendix D for the render directives specific to this document).

14.1 Functional requirements

Generated HTML applications must: be fully navigable; provide working links and controls; avoid dead sections and placeholder actions; show meaningful empty states; validate user input; provide error feedback; preserve state where expected; support keyboard operation; behave correctly at common viewport sizes; avoid console errors; load without missing assets.

14.2 Semantic HTML

Use native semantic elements where possible: header; nav; main; section; article; aside; footer; button for actions; a for navigation; correctly associated label and form controls; valid heading hierarchy. ARIA should supplement, not replace, correct native semantics.

14.3 Accessibility

Minimum target: WCAG 2.2 AA where applicable.

Requirements: keyboard access for all interactive elements; visible focus indicators; sufficient colour contrast; meaningful alternative text; accessible names for controls; no information conveyed only by colour; form error association; skip navigation where appropriate; reduced-motion support; correct modal focus management; screen-reader understandable status updates.

14.4 Responsive design

The implementation must be tested at minimum at: 360 px width; 768 px width; 1024 px width; 1440 px width. The design must avoid horizontal scrolling for normal content and preserve primary actions on small screens.

14.5 JavaScript engineering

Avoid global mutable state. Use event delegation where appropriate. Validate DOM selectors before use. Handle asynchronous errors. Prevent duplicate event binding. Separate data, state, rendering, and event logic. Escape untrusted content. Use textContent rather than innerHTML unless sanitised HTML is explicitly required. Preserve URL and browser history semantics for navigable applications.

14.6 Self-contained HTML requirements

Where the requested deliverable is a self-contained HTML file:

  • embed required CSS and JavaScript;
  • do not rely on unavailable local assets;
  • minimise external CDN dependency;
  • provide graceful fallback when an external service is unavailable;
  • include seeded sample data sufficient to exercise all screens;
  • ensure all navigation works when opened directly from the filesystem, unless a local server is explicitly required;
  • clearly state browser or server requirements.

14.7 Frontend validation

The agent must validate: HTML syntax; no duplicate IDs; navigation targets; button actions; form submission; search and filter behaviour; theme toggle persistence; responsive layout; keyboard paths; console errors; inaccessible labels; broken images or resources; empty result states; reset and recalculation logic; direct loading and refresh behaviour.

14.8 Visual design principles

Prefer clarity over decoration. Use a consistent spacing and type scale. Maintain clear information hierarchy. Limit competing calls to action. Make system status visible. Distinguish editable, computed, and read-only values. Explain units and calculation assumptions. Use charts only where they improve comprehension. Do not rely on animation to explain core logic.

14.9 HTML test evidence

For interactive HTML, the outcome package should include: tested user journeys; browser or automation method; viewport coverage; console status; accessibility check status; known limitations; screenshots where useful; unresolved defects.

15. Harness Design Patterns

15.1 Deterministic shell, probabilistic core

Use deterministic software around model reasoning.

Validate input -> Model proposes -> Schema validates -> Policy checks
-> Tool executes -> Deterministic verifier -> State transition

Best for high-value workflows where interpretation is needed but execution must remain controlled.

15.2 Plan-execute-verify

Separate planning, action, and verification. Planner decomposes the goal. Executor performs one bounded step at a time. Verifier independently checks evidence and completion. Avoid using the same unconstrained model response as both producer and final authority.

15.3 Graph with explicit repair loop

Implement -> Test -> Pass? -> Complete
                | No
                v
             Diagnose -> Repair -> Test

The loop must include maximum iterations, failure classification, and escalation.

15.4 Approval gateway

Place a durable interrupt before high-risk tools.

Proposed action -> Policy -> Approval request -> Human decision -> Execute

The proposed arguments must not change between approval and execution without re-approval.

15.5 Capability token

Issue short-lived, task-scoped capabilities instead of exposing broad credentials. A capability may bind: principal; task; tool; target resource; permitted operation; expiry; budget; environment.

15.6 Read-plan-write separation

Use different permission phases: (1) read-only discovery; (2) plan approval or validation; (3) scoped write grant; (4) verification; (5) grant revocation.

15.7 Branch-and-merge execution

For code and configuration changes, isolate work in a branch or workspace. Merge only after tests and policy checks.

15.8 Evidence-first action

Define required evidence before execution. The agent cannot mark a step complete until evidence is attached.

15.9 Model router

Use small models for classification and extraction, stronger models for architecture or debugging, and deterministic code for validation.

15.10 Context firewall

Separate untrusted retrieved content from control instructions. Treat web pages, documents, issue text, and repository comments as data, not as executable instructions.

15.11 Event-sourced agent state

Record each state transition as an event, allowing replay, forensic analysis, and branch comparison.

15.12 Shadow execution

Run a new model, prompt, workflow, or policy version in parallel without side effects. Compare its proposed decisions against production behaviour.

15.13 Simulation tool

Provide test doubles for every side-effecting tool so evaluation suites can run without changing real systems.

15.14 Circuit breaker

Stop execution when error rate, cost, loop count, latency, or policy violations exceed a threshold.

15.15 Compensating transaction

When true rollback is unavailable, define an explicit action that reverses or neutralises the prior effect.

15.16 Durable task-queue mediation

At fleet scale, an agent task must never execute synchronously inside the process that received the request. Use a mediated architecture: the entry point (an API or webhook) durably persists the task as an event on a message bus or broker before any execution begins, and a separate, independently scalable worker pool consumes those events and performs the actual agentic loop.

This separation exists specifically to survive the failure modes that only appear once execution leaves a single machine: a worker process crashing mid-task, the compute underneath a worker being reclaimed, or a network partition between the worker and a dependent service. Because the task was durably persisted before a worker picked it up, a crashed worker's task can be re-queued and resumed — from the last durable checkpoint (§19.5), not from the beginning — by a different worker, without operator intervention and without losing completed work.

Minimum requirements: the entry point must not execute the agentic loop in-process; the queue/broker must durably persist the event before acknowledging intake; workers must be stateless with respect to the task (all task state lives in the durable store, not in worker memory) so that any worker can resume any task; and the execution environment (sandbox, filesystem) must itself be externally mounted or checkpointed, not local to the worker, so that a worker's death does not destroy in-progress file or command state.

15.17 Companion (trainer) agent

A production harness accumulates traces faster than humans can review them. The pattern that closes the improvement loop (Ch 20, Ch 22) at scale is a companion agent — sometimes called a trainer agent — that continuously mines completed production traces for the most expensive-but-successful runs, replays them against checkpoints to test cheaper or faster alternatives (fewer tool calls, a smaller model, a different tool choice), and proposes — or, under appropriate release gates, applies — the resulting optimisation.

This is a genuine extension of the evidence-first, evaluation-driven posture in §6.9 and Ch 20, not a shortcut around it: a companion agent's proposals must still pass the same release gates (§20.4) as a human-proposed change, and — per §15.12 (shadow execution) — a replayed run with a substituted model or tool is a counterfactual estimate, not a guarantee, because the original trace can never prove what would have happened had a different model been in the loop from the start (see §20.3's replay caveat, extended in this version). Treat a companion agent as a way to generate well-evidenced candidates for improvement at a volume humans cannot match, not as an autonomous authority to promote its own changes to production.

16. Anti-Patterns

16.1 Prompt-only security

Telling the model not to perform an action is not an access control mechanism.

16.2 One universal agent

A single agent with every tool, every data source, and broad permissions creates excessive context, poor tool selection, and unacceptable blast radius.

16.3 Hidden state in conversation history

Important state becomes difficult to validate, migrate, query, or recover.

16.4 Direct model-to-production access

The model must not directly hold persistent production credentials or bypass tool-level policy.

16.5 Automatic retry of side effects

Retries can duplicate payments, tickets, messages, deployments, or database changes.

16.6 Success by self-assertion

An agent statement that work is complete is not verification.

16.7 Unbounded autonomy

No maximum steps, cost, duration, scope, or tool count creates operational and financial risk.

16.8 Tool schemas as documentation only

Schemas must be enforced at runtime.

16.9 Framework lock-in throughout the codebase

Embedding framework-specific message and state objects everywhere makes migration expensive.

16.10 Long prompts as architecture

A large instruction file cannot replace typed state, tools, policy, workflows, and tests.

16.11 Production learning without release controls

Self-modifying code or instructions must not be activated directly in production without review, testing, signing, and rollback.

16.12 Evaluating only final answers

A correct final answer may result from unsafe or expensive intermediate actions. Evaluate trajectories, tool use, policy compliance, and evidence.

17. Self-Extension & Self-Modification

Minimal extensible harnesses demonstrate that agents can create new tools, extensions, or workflow logic. This is powerful but must be governed.

Need identified
-> Agent proposes extension specification
-> Generate code in isolated branch
-> Compile and test
-> Static and security analysis
-> Capability review
-> Human or policy approval
-> Package signing
-> Publish to controlled registry
-> Deploy to non-production

17.2 Prohibited behaviour

An agent must not: silently change its own production policy; grant itself new tools; expand its own permissions; disable audit logging; modify evaluation thresholds; alter approval rules; deploy unreviewed executable code; retain secrets in generated extensions.

18. Security Architecture

18.1 Threat model

The harness must account for: prompt injection; indirect prompt injection from retrieved content; malicious tool output; credential theft; cross-tenant data leakage; excessive agency; command injection; package supply-chain attacks; sandbox escape; data exfiltration; model-provider data leakage; poisoned memory; unauthorised self-modification; approval spoofing; audit tampering; replay attacks; denial of wallet through excessive model usage; denial of service through loops or large outputs; malicious external agents; compromised plugins or MCP servers; insecure generated code.

18.2 Identity model

Every run must have: initiating principal; executing agent identity; delegated authority record; tenant; environment; purpose; expiration; correlation identifier. Agents should have service identities separate from human identities.

18.3 Secret management

Store secrets only in an approved secret manager. Inject short-lived credentials at tool execution time. Never include secrets in model context unless strictly unavoidable. Mask secrets in logs and evidence. Bind credentials to the minimum resource and operation. Rotate and revoke credentials automatically. Scan generated output for accidental secrets.

18.4 Network controls

Deny outbound network access by default. Allowlist destinations by tool or task. Proxy and inspect external requests where appropriate. Block link-local, metadata, and internal control-plane endpoints. Apply DNS and IP controls. Record destination, method, and data classification.

18.5 Data controls

Classify data before model use. Route sensitive tasks only to approved models and regions. Apply minimisation and redaction. Preserve source-level access control during retrieval. Prevent one tenant's memory from entering another tenant's context. Apply retention and deletion policies to prompts, traces, and artifacts.

18.6 Supply-chain controls

Pin dependencies. Use lockfiles. Verify package provenance. Scan packages and images. Restrict runtime package installation. Use signed sandbox images. Maintain software bills of materials. Review agent-generated dependency additions.

19. Reliability & Recovery

19.1 Reliability objectives

Each agent class must define: availability target; task success target; maximum completion latency; maximum cost; maximum recovery time; acceptable intervention rate; acceptable false action rate; evidence completeness target.

19.2 Durable execution

Long-running tasks must persist state after every consequential step. Process restarts must not cause loss of completed work or duplicate unsafe actions.

19.3 Retry policy

Retries must consider: error class; idempotency; side effects; elapsed time; remaining budget; prior attempts; provider health; alternate model or tool availability. Use exponential backoff and jitter for safe transient failures.

19.4 Loop detection

Detect loops through: repeated tool and argument signatures; repeated state hashes; no-progress counters; repeated error classes; increasing context without new evidence; cost threshold; maximum graph traversals.

19.5 Checkpoint and rewind

A checkpoint should include: workflow position; typed state; tool results; artifact references; capability grant state; model and prompt versions; policy version; budget usage. Rewinding must create a new branch of execution rather than rewriting history.

19.6 Disaster recovery

The platform must define backup, restore, region recovery, key recovery, and evidence retention procedures for state and artifact stores.

PART IV — PROVE

Part IV TL;DR

Evaluation is how autonomy is justified. Five evaluation layers — component, task, trajectory, system, human outcome — must all be present before an agent is considered production-ready. Deterministic checks (compile, tests, schema, security scanners) rank above model-based judges. Observability spans nine metric categories, from outcome and autonomy through to context and product. A harness is production-ready only when a twenty-point Definition of Done is complete — not before.

20. Evaluation Engineering

Evaluation is the mechanism through which autonomy is justified.

20.1 Evaluation layers

Component evaluation. Tool schema adherence; retrieval relevance; structured output validity; policy correctness; sandbox isolation; state transitions.

Task evaluation. Objective completion; acceptance-test pass rate; factual accuracy; code correctness; evidence completeness.

Trajectory evaluation. Correct tool selection; unnecessary step count; unsafe intermediate actions; recovery behaviour; context use; policy compliance.

System evaluation. Cost; latency; concurrency; resilience; tenancy isolation; operational recoverability.

Human outcome evaluation. Usefulness; trust; review effort; time saved; intervention quality; business outcome.

20.2 Evaluation dataset

Each production agent should have a versioned suite containing: representative normal tasks; difficult edge cases; ambiguous tasks; malicious inputs; prompt injections; tool failures; partial data; stale data; permission-denied cases; recovery cases; cost stress cases; regression cases from incidents.

20.3 Golden tasks and dynamic judges

Use deterministic checks wherever possible. Model-based judges may supplement but must not be the only quality gate for objective properties.

Example hierarchy:

  1. Compile/build result
  2. Unit and integration tests
  3. Schema checks
  4. Security scanners
  5. Rule-based assertions
  6. Human rubric
  7. Model judge

The counterfactual-replay caveat. Checkpoint-based replay (§15.11, §19.5) makes it tempting to test "what if" changes by resuming a real production trace from the middle with a different model or tool substituted in. Treat the result as a useful signal, not a controlled experiment: the original trace's later steps were shaped by everything the original model or tool did up to that checkpoint, and a different model dropped in mid-trace did not have the opportunity to reach that checkpoint on its own terms — it may never have arrived at the same state at all. A harness-difference confound applies too: substituting a different model into the same harness changes tool-call conventions and formatting the harness may not handle identically (see §2.6). Mid-trace replay is a legitimate way to generate candidate improvements cheaply and at volume (§15.17), but a candidate found this way must still be validated with a full, from-scratch run through the same release gates (§20.4) as any other proposed change before it is trusted.

20.4 Release gates

A new agent, model, prompt, workflow, or tool version must not be promoted when: critical safety tests regress; task success falls below threshold; cost exceeds policy without approved trade-off; evidence completeness falls; cross-tenant or access-control tests fail; rollback or recovery tests fail.

20.5 Online evaluation

Use: shadow runs; canary release; limited tenant rollout; action sampling for human review; anomaly detection; outcome feedback; incident-triggered replay.

22. Definition of Done for a Production Harness

A harness is production-ready only when:

  • architecture and trust boundaries are documented;
  • all tools have typed and versioned contracts;
  • write actions are policy-controlled;
  • execution is sandboxed where arbitrary code can run;
  • state is durable and recoverable;
  • identities and delegated authority are traceable;
  • secrets are short-lived and scoped;
  • every consequential action produces evidence;
  • task, trajectory, security, and recovery evaluations exist;
  • regression gates run in CI/CD;
  • model and prompt versions are pinned and traceable;
  • cost, latency, quality, and intervention are observable;
  • rollback, cancellation, and kill-switch procedures are tested;
  • operational ownership and SLOs are defined;
  • incident response and forensic procedures are documented;
  • data retention and deletion are implemented;
  • tenant isolation is verified where applicable;
  • accessibility and usability of approval interfaces are tested;
  • product limitations are disclosed.

PART V — ADOPT

Part V TL;DR

Enterprise adoption requires platform administration, developer experience, operations, and governance capabilities as first-class product features. ISVs need multi-tenancy, extensibility, configuration, metering, and product compatibility on top of that. External agent interoperability is emerging as a design axis. Build/buy/compose decisions should follow strategic criteria — not vendor claims. A four-phase delivery roadmap moves from discovery through platformisation to ecosystem scale. The maturity ladder pairs A0–A5 autonomy with L0–L5 platform maturity; do not pursue high autonomy at low maturity.

23. Enterprise Product Requirements

An enterprise harness should include:

Platform administration. Organisation, tenant, project, and environment hierarchy; role-based and attribute-based access control; central policy management; agent and tool catalog; model provider configuration; usage quotas and budgets; audit search and export; retention configuration; incident controls and kill switch.

Developer experience. CLI and SDK; local runtime; simulation tools; scaffolding templates; test harness; replay debugger; trace viewer; schema generation; tool mocking; workflow visualisation; extension packaging.

Operations. Run console; pause, resume, cancel, retry, and rewind; queue and concurrency management; health dashboards; cost analytics; model and tool performance; alerting; incident forensics.

Governance. Approval matrices; agent risk classification; release attestations; model allowlists; policy exceptions; periodic access review; compliance evidence export; data lineage.

24. ISV Product Requirements

An ISV harness must add product-grade capabilities.

24.1 Multi-tenancy

Tenant-isolated state, memory, evidence, and artifacts; tenant-specific encryption boundaries where required; noisy-neighbour controls; tenant-specific policies; tenant-owned model keys as an option; regional tenancy; tenant deletion and export.

24.2 Extensibility

Stable extension SDK; versioned tool contracts; tenant-installed extensions; signed package registry; capability declarations; compatibility testing; deprecation lifecycle; extension billing hooks.

24.3 Configuration

Customers should be able to configure: allowed actions; approval rules; business vocabulary; data connectors; model preferences; cost limits; memory policy; evidence retention; escalation paths; UI branding where appropriate. Configuration must not permit bypassing platform safety boundaries.

24.4 Metering and pricing

The platform should meter: model tokens and calls; agent runtime duration; sandbox compute; storage; tool invocations; workflow runs; premium connectors; evaluation runs; human review services; business outcomes where contractually appropriate.

Potential pricing models. Per user; per task; per successful task; per runtime hour; consumption plus platform fee; tenant subscription with included usage; outcome-based pricing; managed operations fee. The cost model must make model, runtime, infrastructure, and service margins visible.

24.5 Product compatibility

Agent behaviour must be versioned; existing customer workflows must not silently change after model upgrades; tenants need controlled opt-in to major behaviour changes; old run state must remain readable or migratable; extensions require compatibility ranges.

25. External Agent Interoperability

Software products will increasingly be accessed by external agents. A harness should therefore expose agent-friendly interfaces.

Requirements. Machine-readable action schemas; stable resource identifiers; explicit preconditions and side effects; price, policy, and constraint metadata; idempotency support; delegated authorisation; consent and approval flows; result provenance; rate and budget controls; anti-abuse controls; external-agent identity; transaction receipts; dispute and rollback mechanisms.

Interaction surfaces should be distinguished. Human UI; first-party agent UI; internal agent APIs; external agent APIs. Do not expose internal unrestricted tools directly to external agents.

26. Worked Examples

26.1 Example 1 — Coding Harness

Objective. Implement a feature in an existing repository and create a pull request.

Flow.

Task intake
-> Read-only repository inspection
-> Architecture and instruction retrieval
-> Baseline build and tests
-> Change plan
-> Policy validation
-> Isolated branch and sandbox
-> Code modification
-> Unit/integration/browser tests
-> Static and security scans
-> Diff review
-> Pull request creation
-> Human review

Required tools. Repository search; file read; patch apply; build; test; lint; type check; dependency scan; secret scan; browser test; pull request create.

Completion criteria. Acceptance tests pass; no new critical security issues; diff is scoped; pull request contains evidence; no direct main-branch write.

26.2 Example 2 — Enterprise Service-Desk Agent

Objective. Resolve common access or configuration incidents.

Pattern. Read incident; retrieve authorised user and asset context; classify request; select approved runbook; propose action; require approval for privileged changes; execute via bounded tool; verify outcome; update ticket with evidence; escalate when verification fails.

Guardrails. No free-form shell on production systems; no standing administrator credential; all changes through approved automation; user identity verified; change window enforced; rollback runbook attached.

26.3 Example 3 — ISV Customer Configuration Agent

Objective. Allow a customer administrator to describe a desired workflow in natural language.

Flow.

Intent capture
-> Convert to typed configuration proposal
-> Validate against tenant entitlements
-> Simulate workflow
-> Show diff and impact
-> Customer approval
-> Apply versioned configuration
-> Run smoke tests
-> Activate progressively

The agent generates configuration but cannot bypass the product's schema, entitlements, or policy engine.

26.4 Example 4 — Self-Extending Developer Harness

Objective. Add an audit event whenever a file-deletion tool is used.

Safe implementation.

  1. Inspect extension SDK and current tool lifecycle events.
  2. Generate a TypeScript extension in an isolated branch.
  3. Subscribe to pre-delete and post-delete events.
  4. Emit structured audit records without recording file contents unnecessarily.
  5. Add unit and integration tests.
  6. Test failed deletion and partial failure.
  7. Verify no recursive event loop.
  8. Run security and dependency checks.
  9. Package and sign the extension.
  10. Deploy to a test environment.
  11. Enable for selected users.
  12. Promote after evaluation.

The agent may author the extension. The harness controls whether it becomes active.

27. Build, Buy, or Compose

27.1 Build custom when

Harness behaviour is core product differentiation; regulation requires deep control; specialised execution or data boundaries exist; very high scale justifies optimisation; existing platforms cannot support the required extension model; long-term platform ownership is strategic.

27.2 Buy managed when

Speed is more important than differentiation; use cases are conventional; managed compliance and operations create value; the organisation lacks platform engineering capacity; vendor lock-in and pricing are acceptable.

27.3 Compose open-source components when

Custom product behaviour is required; the organisation can operate distributed systems; a replaceable framework strategy is desired; open-source licensing is suitable; internal teams can own security and reliability hardening.

27.4 Recommended default

Use a composable architecture: open-source or managed orchestration framework; product-owned tool and policy contracts; managed or standard workflow persistence; hardened sandbox service; central model gateway; independent evaluation and evidence platform.

28. Delivery Roadmap

28.1 Phase 0 — Discovery and control definition (2 to 4 weeks)

Deliverables. Use-case inventory; risk classification; task contracts; autonomy levels; target architecture; framework assessment; policy baseline; evaluation baseline; cost model.

30. Maturity Model

Level Name Characteristics
0 Experiment Standalone prompts, manual execution, no persistent evidence
1 Bounded agent Limited tools, local sandbox, basic tests, human supervision
2 Managed harness Central model gateway, typed state, policy, durable traces, approvals

31. Key Strategic Decisions

Every harness programme must explicitly decide:

  1. Which actions remain deterministic?
  2. Which decisions may be delegated to a model?
  3. What is the highest permitted autonomy level?
  4. What evidence proves completion?
  5. Which state is short-lived, durable, or prohibited from retention?
  6. Which tools can change systems of record?
  7. What requires human approval?
  8. How is execution isolated?
  9. How are model and framework dependencies abstracted?
  10. How are changes evaluated and promoted?
  11. How are tenants isolated?
  12. How is cost allocated and priced?
  13. How can the agent fail safely?
  14. How can operations be reversed?
  15. Which harness assets create proprietary advantage?

32. Recommended Engineering Position

Treat harness engineering as a product platform capability with three layers:

32.1 Layer 1 — Common control platform

Identity, model gateway, policy, state, sandboxing, audit, evaluation, telemetry, and cost management.

32.2 Layer 2 — Domain execution kits

Tools, skills, workflow patterns, schemas, knowledge connectors, evaluation packs, and approval templates for software engineering, customer support, commerce, finance, operations, or other domains.

32.3 Layer 3 — Product and client solutions

Specific agents, user journeys, external interfaces, and business outcomes built using the common platform and domain kits.

This avoids two extremes: a monolithic universal platform that cannot adapt to domain needs; and isolated project agents that cannot meet enterprise controls.

33. Conclusion

Agent frameworks make it easier to express model-driven workflows. Harness engineering makes those workflows operable, secure, testable, and commercially viable.

The near-term opportunity is to standardise how agents receive context, invoke tools, execute code, persist state, produce evidence, and pass quality gates. The longer-term opportunity is larger: the harness can become the programmable operating layer through which software systems interpret goals and coordinate work.

This transition does not reduce the importance of software engineering. It increases it. As models generate more implementation, software engineers must build stronger contracts, clearer architectures, safer execution environments, better tests, more reliable state machines, richer observability, and more disciplined product controls. The competitive question will move from "Which model do we use?" to:

How effectively does our harness convert changing model capability into reliable, differentiated, and governable software outcomes?

Appendix F — Glossary

F.1 Harness engineering terms (from Ch 5, extended)

Term Definition
Agent A software actor that uses a model to interpret a goal, decide or select actions, invoke tools, observe outcomes, update state, and continue until completion, escalation, or termination.
Agent framework A development abstraction used to define agent behaviour (prompts, graph nodes, tool schemas, model calls, routing logic).
Agent harness The concrete runtime, control plane, execution plane, and engineering environment in which an agent operates.
Agent platform A productised collection of harness services, developer tooling, operations tooling, governance, deployment capabilities, and reusable components used to build and run multiple agents.
Autonomy level (A0–A5) The scale of permitted independent action, from advisory (A0) to delegated authority (A5). See Ch 8.
Capability grant / token A short-lived, task-scoped credential binding principal, task, tool, resource, expiry, and budget.
Checkpoint Recoverable snapshot used to resume, inspect, branch, or rewind execution.
Companion (trainer) agent An agent that continuously mines production traces for expensive-but-successful runs, replays them to test cheaper or faster alternatives, and proposes or (under release gates) applies optimisations. See §15.17.
Context engineering The design of what information, instructions, tools, examples, policies, state, memory, and environmental observations are made available to a model at each step.
Context firewall A pattern that separates untrusted retrieved content from control instructions.
Coupled / decoupled harness A model-coupled harness is trained or tuned alongside a specific model family for higher tool-call accuracy at the cost of portability; a model-decoupled harness is deliberately model-agnostic for portability and supply-chain resilience at some cost to peak performance. See §2.6.
Durable task-queue mediation The pattern of persisting a task as an event on a message bus before execution, so a stateless worker pool can pick it up, crash, and be resumed by another worker without losing progress. See §15.16.
Evidence Machine-generated proof of an agent action or result (logs, diffs, command output, test results, screenshots, API responses, approvals, traces, checksums, signed artifacts).
HIL (Human-in-the-Loop) Mandatory approval gate between AI agent action and production; a first-class workflow state, not an exception.
Idempotency Property of an operation such that applying it multiple times yields the same result as applying it once.
Model gateway A centralised abstraction over provider-specific model APIs providing routing, budget, retention, and governance.
Policy engine A component external to the model that evaluates every consequential action for allow / deny / require-approval / substitute outcomes.
Sandbox An isolated execution environment that limits filesystem, process, network, identity, and resource access for generated code or agent actions.
Shadow execution Running a new model, prompt, workflow, or policy version in parallel without side effects to compare its proposed decisions against production.
Skill A reusable package of instructions, examples, tool usage guidance, domain conventions, and optional executable resources.
State (run / working / long-term / knowledge / evidence / artifact) The seven-class taxonomy used to categorise durable and transient information; see §10.9.
Task contract The immutable typed representation of an agent's job, including objective, inputs, constraints, evidence requirements, and completion criteria.
Tool A typed, bounded capability exposed to an agent.
Trajectory The sequence of steps, tools, arguments, and observations an agent produces to reach an outcome. Evaluated distinctly from the final answer.
Workflow A defined sequence or graph of states and actions, including branches, loops, gates, retries, approvals, and terminal conditions.
